# 09 — Non-Blocking Settlement

**Doctrine:** Tenets 3, 7, 11. Settlement is a property of the notification layer, never of a call site. A wall-clock bound placed where a lifecycle signal belongs converts a stall into a silent lie; the fix is to remove the clock, not tune it.

## Evidence (pre-cutover, 2026-09-12 field repro)

- Two clocks raced on one session: spawn armed 300s (`timeoutHandle`), `task_continue` stacked a 120s bound on the same task; the shorter one expired first and drove the task into `timed_out_retained` — a terminal state with no outgoing edge — permanently deafening the ledger to the child's real outcome.
- The child never died (`timeoutBehavior: "notify"`); its findings arrived only because the operator pasted them out-of-band. A green `task_result` frozen at 11 messages across four reads was the falsifiable signature.
- Notification text reported `config.defaultTimeoutMs` (900s) for a 300s bound: `ActiveTaskState` never carried the per-call value. The reviewer's validated triage (56 findings) sorted the rest of the timer funnel into "delete, don't fix" — see the cutover acceptance list.

## Decisions

- **No per-call clocks, anywhere.** `src/shared/bound.ts`, `handleTimeout`, `awaitContinuation`, `timeoutBehavior`, `timeout_ms`, `await_response`, and the timeout states are deleted — not defaulted, not widened. The only sanctioned waits are the notification gate's fixed retry backoff and lazy TTL expiry on read paths. The only bound on a child is operator intent via `task_interrupt`.
- **Tools are pure verbs.** `dynamic_task` spawns and returns; `task_continue` sends and returns (settle → revival via the single `reviveRetainedTask` choke point; active → refuse "still running"; interrupted → refuse, spawn fresh); `task_status`/`task_list` are store reads, while `task_result` is a live read — it calls `session.get`/`session.messages` (as the README row says) and falls back to store state only when the API itself errors. Each settled turn notifies exactly once as a `[dynamic-task-notify]` message.
- **Prompt failure is not settlement — retryable failure leaves the task active.** A fired child prompt that rejects with a retryable transport error (ETIMEDOUT, ECONNREFUSED, fetch failed, timeout…) says nothing about the child: the turn may well be running, and settling error would deafen the ledger to the child's genuine terminal event. The task stays active and its lifecycle event settles it. Only non-retryable failures (unknown session, permission, synchronous throw) settle error and notify. The bound for a truly-dead child stays operator `task_interrupt` — there is no clock to rescue it and none is wanted.
- **One child→parent channel.** `task_notify` is general communication; "blocked" is a payload, not a tool (ruling: purpose-specific signal tools rejected). Notices carry a separate dedup kind, so a notice never consumes the child's settlement slot — the task stays active and still reports on completion.
- **Exactly-once lives in `gateLedger`** (`src/shared/notify.ts`): synchronous in-flight claims plus `(childSessionId, dedupKey)` keys bound to a per-child generation. `forgetChild` on revival bumps the generation and clears the child's pending claims; every claim records the generation it won and every commit carries it back — a commit from before the bump emits its history record but can never reserve or release the revived turn's keys, so a predecessor's late-successful retry cannot suppress the new turn's settlement. Same-child deliveries additionally serialize in claim order (per-child chain, FIFO-capped at the same 1000-child window as the dedup gate — an evicted child keeps delivery, loses ordering), so a stale retry can never land after a newer turn's message. A failed delivery does not reserve the key (redelivery stays possible); a suppressed duplicate records `suppressed: true` and a parentless settlement records attempts 0 with parent `unknown` — `task_result` renders "Suppressed (duplicate — already delivered)" and "Not delivered (no parent session)" respectively, never FAILED: suppression and nowhere-to-dial are honest outcomes, not failed dials. The state-machine settlement itself is single-winner and terminal — recovery rides `task_continue`, and the FAILED record surfaces via `task_result`. Dedup holds for the most recent 1000 children; evicted keys may re-deliver verbatim repeats — bounded memory, documented window.
- **Record renders are truthful about outcome.** The notifier writes `delivered`/`attempts`/`suppressed`; the formatter distinguishes four states — delivered, FAILED (a real attempt failed), suppressed duplicate, parentless non-delivery. The notification ledger is in-memory process state (no persistence, no migration).
- **Agent discovery is scoped per client.** `fetchAgents` caches in a `WeakMap` keyed by session client with a TTL, replacing the process-global cache that let one plugin instance serve another client's agent list; `resetAgentCache` invalidates every client's entries via an epoch bump (WeakMaps are not enumerable).
- **Interrupt order:** transition to `interrupted` synchronously BEFORE calling the server abort, so the abort's own idle events can never be misclaimed as a completion. A 404 settles interrupted (dead means dead); an abort transport failure withdraws the speculative claim back to active so the genuine terminal event still settles it — unless a newer abort already landed (`lastAbortAt` guard: success is knowledge, failure is ignorance — same-millisecond successes supersede too, `>=` not `>`) or the slot is gone. Withdrawal persists via the ledger observer. Settled history records the gap without disturbance (success records are never annotated). Interrupting an already-settled task reports the settled state truthfully.
- **`deleted` is a failure** — normalized in `resolveNotifyKind` at the single kind-resolution site, and the settlement kind follows the settled outcome (not raw status text), so a deleted session with stale `idle` status still notifies error.
- **Durability is strict at the boundary:** ledger saves are tmp+rename (no residue); the reader rejects key-divergent, non-finite, and mixed-lineage entries wholesale; boot restore honors the configured retention cap.

## Invariants

- `safety-invariants` scanner forbids: `setTimeout`/`setInterval` in `src/**` except the notify retry and test-only seams — and the whitelist is counted: `notify.ts` keeps exactly ONE timer-shaped call site (the retry's `defaultSleep`); `await_response`, `timeout_ms`, `timeoutBehavior` anywhere; lifecycle field writes (`.state`/`.abortError`/`.lastAbortAt`/`.lastNotice` assignments) outside `task-state.ts` — reads stay free, writes funnel through the state machine.
- README tool rows ↔ `tool({` registrations are checked in both directions (cycle 00 invariant, extended).

## Verification

Follow-up 2026-09-22 (orchestration audit + parent→child steer, spec in `tasks/10-parent-steer.md`): `task_continue` on an active task no longer refuses "still running" — it steers (synchronous claim, abort, parent text as the next turn, task stays active; the lifecycle handler consumes the aborted turn's echo). The lifecycle-field scanner now also covers `steerPending` writes outside `task-state.ts`. `task_result` for tracked tasks reports store state as `Status` with the live read as an advisory block (see 05). Concurrent steers on one child are knowingly unserialized (documented in 10); the create/abort entry funnel covers spawn/interrupt/steer paths.

- Suite: 294 tests green; `tools.integration.test.js` rewritten to settle children by firing lifecycle events — tests never wait on clocks, they wait on microtasks.
- `DYNAMIC_TASK_BLOCKED_AGENTS=""` (empty env) cannot clear the default blocklist; an explicit `blockedAgents: []` in options/file can — the latter is a real setting, the former is an absent value.
- Live gate: restart → spawn → notify → settle → continue → settle → interrupt (pending operator run).
